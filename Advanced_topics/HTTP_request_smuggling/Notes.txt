HTTP Request Smuggling:
- Technique for interfering with the way a website process sequences of requests that received from one or more users
- Impact: allow attacker to bypass security control, gain unauthorized access to sensitive data and directly compromise other application users
- Primarily associated with HTTP/1, but HTTP/2 sites may also be vulnerable depending on BE architecture

Context:
- Simple architecture that frequently used in modern applications
    Client -> FE server (load balance or reverse proxy) -> BE server
- When FE forward request to BE, it typically send several request over same connection -> much more efficient and performant
    + HTTP requests are sent one after another and receiving server has to determine where request end and next begin
    + If FE and BE have different rule of boundary between requests -> attacker could send ambiguous request and get interpreted differently by FE and BE systems

How this vuln arise:
- Because the HTTP/1 specification provides two different ways to specify where a request ends:
    + Content-Length header: specify length of message body in bytes
    + Transfer-Encoding header: specify that the message body uses chunked encoding. Message body could contain one or more chunks of data, each chunk consist of chunk size in bytes (expressed in hexadecimal), followed by newline and chunk contents. It terminated with chunk of size 0
    + Note:
        + Many security testers are unaware that chunked encoding can be used in HTTP requests, for 2 reasons:
            + Burp Suite automatically unpacks chunked encoding to make messages easier to view and edit
            + Browsers do not normally use chunked encoding in requests, and it is normally seen only in server responses
- Possible for single request use both CL and TE at once
    -> So the specification attempts to prevent this problem by ignore one
- Problem: if two or more servers are chained together can cause different behavior in determine boundary between requests
- Note:
    + Web that use HTTP/2 end-to-end are immune to this attack. As it introduce a single, robust mechanism for specifying length of request
    + But many web have HTTP/2 in FE server, but BE only support HTTP/1
        -> FE must translate request by downgrading into HTTP/1 -> vuln

How to perform attack:
- Classic method is placing both CL, TE headers into single HTTP.1 request and modify body to cause different behavior between FE and BE
- 3 ways that can happen:
    + CL.TE: FE uses CL, BE uses TE
    + TE.CL: FE uses TE, BE uses CL
    + TE.TE: both support TE, but one can be induced not to process it by obfuscating the header in some way
- Note:
    + These techniques only work with HTTP/1 request
    + Burp and browsers default to HTTP/2 when server advertises support via TLS handshake
    + When testing HTTP/2 sites, need manually switch protocol in Burp Repeater > Request attributes > Inspector panel

Identifying vuln using timing techniques:
- Finding CL.TE:
        POST / HTTP/1.1
        Host: vulnerable-website.com
        Transfer-Encoding: chunked
        Content-Length: 4

        1
        A
        X
    + FE forward '1\r\nA' only
    + BE parse chunk of size 1 'A', then wait for next chunk size or \r\n to end the chunk data, but next chunk never arrive -> timeout
- Finding TE.CL:
        POST / HTTP/1.1
        Host: vulnerable-website.com
        Transfer-Encoding: chunked
        Content-Length: 6

        0

        X
    + FE forward '0\r\n\r\n'
    + BE expect 6 bytes, but only get 5 bytes -> wait for 1 more bytes that never arrive -> timeout
- Note: to minimize disruption to other users, should test for CL.TE first, then try to test for TE.CL

- Bypassing client authentication:
    + TLS handshake: (one-way)
        + Client ---> Server (client verify server cert)
        + Server authenticate themselves with client by provide a certtificate contain their "common name" (CN), which match their registered hostname
        + Client can use this to verify that they're talking to a legitimate server
    + Mutual TLS authentication (mTLS): (two-way)
        + Client <---> Server (both need to verify cert)
        + Client must also present a cert to server
        + Client's CN is often a username, which would be used as part of access control mechanism in BE
        + Component that authenticate client typically pass data to BE via one or more non-standard HTTP headers. Example:
            GET /admin HTTP/1.1
            Host: normal-website.com
            X-SSL-CLIENT-CN: carlos
            + These header is hidden from users and implicitly trusted by BE server
            + If can send fake headers and values -> able to bypass access control 
            + In practice, FE will override these headers if they're already present, so it usually unexploitable
    + Smuggled requests are hidden from FE -> any headers contain will be sent to BE unchanged
        POST /example HTTP/1.1
        Host: vulnerable-website.com
        Content-Type: x-www-form-urlencoded
        Content-Length: 64
        Transfer-Encoding: chunked

        0

        GET /admin HTTP/1.1
        X-SSL-CLIENT-CN: administrator
        Foo: x

- Using HTTP request smuggling to turn an on-site redirect into an open redirect: 
    + Redirect victim's request to attacker server
    + Default behavior of Apache and IIS web servers, request to a folder without trailing receives a redirect to the same folder including trailing slash
        GET /home HTTP/1.1
        Host: normal-website.com

        HTTP/1.1 301 Moved Permanently
        Location: https://normal-website.com/home/
    + This behavior is harmless, but it can be exploited to redirect other users to external domain. For example:
        POST / HTTP/1.1
        Host: vulnerable-website.com
        Content-Length: 54
        Transfer-Encoding: chunked

        0

        GET /home HTTP/1.1
        Host: attacker-website.com
        Foo: XGET /scripts/include.js HTTP/1.1
        Host: vulnerable-website.com
        ----------------------------------------
        HTTP/1.1 301 Moved Permanently
        Location: https://attacker-website.com/home/

    + Turning root-relative redirects into open redirects:
        + Some servers use path to construct root-relative URl for Location header (no domain in Location)
            GET /example HTTP/1.1
            Host: normal-website.com

            HTTP/1.1 301 Moved Permanently
            Location: /example/
        + If server allows protocol-relative URL in path -> open redirect
            GET //attacker-website.com/example HTTP/1.1
            Host: vulnerable-website.com

            HTTP/1.1 301 Moved Permanently
            Location: //attacker-website.com/example/
        + Browser interprets //attacker-website.com/ as protocol-relative URL -> navigates to attacker's site
- Using HTTP request smuggling to perform web cache poisoning: (11)
    + If FE caches content -> smuggled redirect response gets cached under victim's requested URL
    + It make attack persistent, affecting all subsequent users request to that URL
    + Victim sent request to static resource, after that it would append to smuggled request but still think that is static resource and get cached

    + Difference between web cache poisoning and web cache deception:
        + Web cache poisoning: store malicious content in cache -> serve to other users
        + Web cache deception: store sensitive content belong to another user -> attacker retrieve it through cached page
    + For example: private message will be cached in /static/some-image.png

Advanced request smuggling:
- HTTP/2:
    + HTTP/2 messages sent as series of separate "frames", each with explicit length field, tell server exactly hơ many bytes to read
    + Request length = sum of frame length -> no ambiguity -> immune to smuggling in theory
    + But only if HTTP/2 end-to-end - HTTP/2 downgrading breaks the protect
- H2.CL vuln: (13)
    + HTTP/2 don't specify their length in header
    + During downgrading, FE add CL header derived from HTTP/2 built in frame length
    + But HTTP/2 can also include their own CL header and reuse it in HTTP/1 request
        + RFC: CL must match built in length, but this isn't always validated properly before downgrading
    + Exploit:
        + FE uses HTTP/2 frame length, BE uses CL when downgrading to HTTP/1
        + Example:
            :method	        POST
            :path	        /example
            :authority	    vulnerable-website.com
            content-type	application/x-www-form-urlencoded
            content-length	0

            GET /admin HTTP/1.1
            Host: vulnerable-website.com
            Content-Length: 10

            x=1
            ---------------Downgrade----------
            POST /example HTTP/1.1
            Host: vulnerable-website.com
            Content-Type: application/x-www-form-urlencoded
            Content-Length: 0

            GET /admin HTTP/1.1
            Host: vulnerable-website.com
            Content-Length: 10

            x=1GET / H

- Response queue poisoning: (14)
    + Cause FE server to start mapping response from BE to wrong request
        -> All users of same connection are served response that were intended for someone else
    + Smuggle a complete request -> BE return 2 response, FE expect only 1 -> response is queued for next request
    + How to construct:
        + Require:
            + TCP connection between FE and BE is reused for multiple request/response cycles
            + Attacker can smuggle a complete request in standalone request
            + Attack must not cause either server to close TCP connection
        + Example smuggling a complete request:
            -------------FE (CL)--------------
            POST / HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            Content-Type: x-www-form-urlencoded\r\n
            Content-Length: 61\r\n
            Transfer-Encoding: chunked\r\n
            \r\n
            0\r\n
            \r\n
            GET /anything HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            \r\n
            GET / HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            \r\n
            --------------BE (TE)----------------
            POST / HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            Content-Type: x-www-form-urlencoded\r\n
            Content-Length: 61\r\n
            Transfer-Encoding: chunked\r\n
            \r\n
            0\r\n
            \r\n
            GET /anything HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            \r\n
            GET / HTTP/1.1\r\n
            Host: vulnerable-website.com\r\n
            \r\n
- Request smuggling via CRLF injection: (15)
    + Even if web prevent by validate CL or stripping TE, still can exploit by using \n to smuggle prohibited headers
    + If BE treat as delimiter, but FE does not -> some servers will fail to detect second header
        Foo: bar\nTransfer-Encoding: chunked
    + HTTP/1: handling full CRLF (\r\n) to terminate header
    + HTTP/2: messages are binary, so boundaries of each header based on explicit, predetermined offsets rather than delimiter characters -> \r\n no longer special and can include inside value
        foo	    bar\r\nTransfer-Encoding: chunked
