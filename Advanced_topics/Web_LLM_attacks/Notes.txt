Web LLM attacks:
- Expose and take advantage of the model's access to data, APIs, user information,...
- Example:
    + Retrieve data LLLM has access to (include LLM prompt, training set, APIs)
    + Trigger harmful action via APIs, could perform SQL injection attack on API has access to
    + Trigger attack on other users and system that query LLM
- At high level, similar to exploiting a SSRF vuln

Detect:
- Identify LLM's input both direct(prompt) and indirect(training data)
- What data and APIs the LLM has access to
- Probe this new attack surface for vulnerabilities

Exploiting LLM APIs, functions, and plugins:
- How LLM APIs work:
    + Step 1: client call LLM with user's prompt
    + Step 2: LLM detect function need to be called and return JSON object contain argument to the external API's schema
    + Step 3: client call function with provided arguments
    + Step 4: client process function's response
    + Step 5: client call LLM again, append the function response as a new message
    + Step 6: LLM call external API with function response
    + Step 7: LLM summarizes the results of API call back to user
    + Note: calling external API on behalf of user, but user may not be aware that these APIs are being called. Ideally, users should be presented with a confirmation step before LLM calling external API
- Mapping LLM API attack surface:
    + Excessive agency: LLM has access to sensitive API and use those unsafely
    + Attacker can push LLM beyond intended scope and launch attacks via APIs
    + First step is to work out which APIs and plugins LLM has access to (Just simply ask LLM)
    + Then ask for additional detail on any APIs of interest
    + If LLM isn't cooperative, providing misleading context and re-asking
- Chaining vulnerabilities in LLM APIs:
    + Even if LLM only has access to harmless API, still be able to use these to find secondary vuln.
    + Example: use LLM to execute a path traversal attack that take filename as input
